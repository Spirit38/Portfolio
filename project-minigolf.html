🎯 Contexte

Stage de développement de 8 semaines chez JKL Events (Mini-Golf de Crolles), un complexe de loisirs immersif. En équipe de 3 développeurs, nous avons reconstruit de zéro l'application numérique de l'établissement : une PWA (application web progressive) remplaçant les fiches de score papier et une ancienne application Firebase vieillissante.

❓ Problématique

Le suivi des parties reposait sur du papier (calculs de points « Énergie Quantique » complexes, erreurs fréquentes, aucune donnée exploitable) et une application obsolète sans fidélisation. Il fallait une solution moderne, fluide sur mobile, sécurisée et exploitable pour le pilotage de l'activité — tout en laissant un joueur saisir ses scores sans créer de compte.

👤 Mon rôle

Au sein de l'équipe, j'ai pris en charge l'essentiel de la partie serveur, des données et de la sécurité :

  • Conception et sécurisation de la base de données PostgreSQL (~20 tables).
  • Développement du back-office d'administration (tableau de bord temps réel, validation des parties, modération).
  • Gamification : succès, récompenses et roue des cadeaux.
  • Système de notifications push et d'emails automatisés.
  • Déploiement et mise en production de l'application.

🧠 Stack technique

React 18 TypeScript Vite Tailwind CSS Supabase PostgreSQL Deno (Edge Functions) PWA
  • Frontend : React + TypeScript en PWA mobile-first (installable, hors-ligne partiel, notifications push) — une seule base de code pour iOS et Android, sans store.
  • Backend : Supabase (BaaS) — base PostgreSQL relationnelle, authentification et moteur temps réel.
  • Serverless : 4 Edge Functions Deno/TypeScript isolant les opérations sensibles (emails via Resend, Web Push, tâche planifiée, suppression de compte RGPD).

🔒 Architecture & sécurité

Principe directeur : l'autorité revient au serveur, jamais au client. La logique est répartie sur trois niveaux de confiance (client / base de données / Edge Functions).

  • RLS (Row Level Security) sur toutes les tables, avec un event trigger activant automatiquement la RLS à la création de toute nouvelle table (aucune table ne reste sans protection).
  • Secret d'équipe : pour autoriser un invité (sans compte) à modifier sa partie sans accéder à celles des autres, chaque équipe reçoit un secret transmis par en-tête HTTP — secret jamais lisible côté client grâce à des privilèges au niveau colonne.
  • Calculs sensibles côté base (victoire, attribution des succès) via des triggers : le client ne peut pas se déclarer vainqueur.
  • Audit & durcissement : un audit pendant le stage a révélé que des Edge Functions ne vérifiaient pas l'identité de l'appelant (envoi d'emails de masse déclenchable par n'importe qui) ; je les ai durcies pour vérifier le rôle via le jeton JWT, non falsifiable.
  • Conformité RGPD : suppression de compte côté serveur, anonymisant le profil tout en conservant les statistiques.

⚙️ Extrait — confidentialité du secret d'équipe (PostgreSQL)

Le secret ne doit jamais fuiter côté client : on retire le SELECT global puis on ré-accorde l'accès colonne par colonne, en excluant la colonne du secret.

sécurité — politiques RLS (PostgreSQL)
-- Le secret d'équipe ne doit jamais être lisible côté client :
-- on retire le SELECT global, puis on ré-accorde colonne par colonne — sauf team_secret.
REVOKE SELECT ON public.teams FROM anon, authenticated;
GRANT  SELECT (id, name, created_by, nb_joueurs, is_finished, share_token)
       ON public.teams TO anon, authenticated;   -- team_secret exclu

-- L'écriture d'un invité n'est autorisée que si le secret (en-tête HTTP) concorde.
CREATE POLICY "Modification_teams" ON public.teams
  FOR UPDATE USING (public.team_write_allowed(id));

🚀 Réalisations clés

  • Attribution automatique des succès en une seule requête SQL transactionnelle (chaînage de CTE) : atomique, idempotente, sans surdistribution de stock — avec le mécanisme inverse de révocation si un score est supprimé.
  • Relance automatique J+20 (Edge Function planifiée) avec gestion fine de l'échec partiel : une équipe n'est marquée « relancée » que si tous ses emails sont partis, sinon reprise le lendemain — traitement auto-correctif.
  • Barèmes de points configurables depuis le back-office, appliqués en temps réel sans redéploiement (repli automatique sur les valeurs du code).
  • Statistiques calculées en base (vues SQL) plutôt que côté client, et tableau de bord temps réel (Supabase Realtime).

🛠️ Déploiement & mise en production

J'ai assuré la mise en production de bout en bout :

  • Build Vite (fichiers statiques versionnés par hachage) hébergé sur Hostinger Business derrière le domaine app.minigolfcrolles.fr.
  • En-têtes de sécurité via .htaccess : HSTS, X-Frame-Options, X-Content-Type-Options, Permissions-Policy et Content-Security-Policy.
  • Configuration DNS : entrées SPF et DKIM authentifiant les emails (sans elles, les relances seraient classées en indésirables).
  • Secrets (clés Supabase / Resend / push) en variables d'environnement, jamais dans le dépôt ; intégration Git pour le déploiement automatique sur push.

🛠️ Ce que j'ai appris

  • Placer la sécurité et l'intégrité directement dans la base (RLS, fonctions à droits du propriétaire, triggers) plutôt que de faire confiance au client.
  • Concevoir des fonctions serverless robustes (gestion des échecs partiels, traitements planifiés).
  • Mener un projet jusqu'à la production réelle (domaine, DNS, services tiers) pour de vrais utilisateurs.
  • Travailler à plusieurs sur une même base de code : intégration propre des modules et documentation des choix.
