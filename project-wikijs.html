🎯 Contexte et Problématique

L'instance Wiki.js de Chartreuse — plateforme centrale de documentation interne — était hébergée sur un service externe présentant des limites en termes de contrôle, de sécurité et de résilience. J'ai pris en charge la migration complète vers une VM interne dédiée, en assurant la continuité du service, la sécurisation des accès (SSL, SSO), la remise en état de l'authentification Microsoft Entra ID post-migration et l'automatisation des sauvegardes.

🧠 Stack Technique & Environnement

Linux Docker & Docker Compose PostgreSQL 17 Nginx acme.sh Let's Encrypt Microsoft Entra ID Bash

🏗️ Conteneurisation & Restructuration du Stockage

  • Migration de volumes : Conversion des volumes Docker autonomes vers une arborescence locale en bind mounts (./wiki-data, ./db-data, ./.db-secret) pour un contrôle direct du stockage et une gestion simplifiée du Plan de Reprise d'Activité.
  • Stack multi-conteneurs : Déploiement coordonné des services wiki, db (PostgreSQL 17) et wiki-update-companion avec gestion stricte des privilèges (UID/GID 1000:1000 pour Wiki.js).

🔒 Certificat SSL & Renouvellement Automatique

Le service étant exclusivement interne, l'obtention d'un certificat Let's Encrypt nécessitait le challenge DNS-01 (impossible de passer par HTTP-01 sur un réseau non exposé).

  • acme.sh + API Infomaniak : Génération et renouvellement automatique du certificat TLS sur le domaine délégué in.chartreuse.eu via l'API DNS Infomaniak, sans exposition publique du serveur.
  • Utilisateur système dédié (acme) : Exécution du processus sous un compte isolé à privilèges réduits pour limiter la surface d'attaque.
  • Rechargement Nginx sans élévation globale : Règle sudoers ciblée permettant au script de recharger le reverse-proxy (systemctl reload nginx) sans accorder de droits root complets.

🌐 Reverse Proxy Nginx & Support WebSocket

  • HTTPS strict : Virtual Host configuré avec TLSv1.2/TLSv1.3, redirection 301 systématique de HTTP vers HTTPS.
  • WebSockets : Passage des en-têtes Upgrade et Connection indispensables au bon fonctionnement de l'éditeur collaboratif temps réel de Wiki.js.

🔑 Diagnostic & Résolution d'Incident SSO (Intervention SQL)

Suite à la migration, l'authentification Microsoft Entra ID (Azure AD) était cassée — les URL de callback et les secrets n'étant plus valides pour la nouvelle instance.

  • Reconfiguration Entra ID en base : Injection directe du nouveau Client Secret et réalignement des URL de callback dans la table authentication de PostgreSQL via des requêtes SQL ciblées, sans accès à l'interface d'administration.
  • Réalignement de la clé host : Mise à jour de la table settings pour forcer la génération correcte des jetons OpenID Connect sur le nouveau domaine.

⚙️ Plan de Reprise d'Activité & Sauvegarde Automatisée

  • Script Bash d'archivage à chaud : Export SQL complet via pg_dump combiné à la compression des assets médias (tar.gz), sans interruption du service.
  • Rétention glissante : Nettoyage automatique des archives de plus de 7 jours pour prévenir la saturation du stockage.
  • Externalisation NAS sécurisée : Synchronisation automatique du dossier de sauvegarde vers le NAS d'entreprise via rsync et authentification SSH par clés Ed25519 non-interactives (zéro mot de passe).
  • Planification Cron : Sauvegardes déclenchées quotidiennement à 03h00, renouvellement SSL automatique à J+60.

🗄️ Nettoyage de Masse de la Base de Données

Après migration, l'ensemble des liens internes de la documentation pointaient encore vers l'ancien domaine hébergeur.

  • Audit SQL : Requêtes d'inspection (SELECT avec conversion de type JSON) pour identifier l'intégralité des références résiduelles vers l'ancien domaine.
  • Refactoring de masse : Remplacement via REPLACE() sur les colonnes content (Markdown) et render (HTML) de la table pages — résultat : 0 lien mort conservé après opération.

🛠️ Savoir-faire acquis

  • Migration d'une application conteneurisée avec continuité de service (< 5 min d'interruption).
  • Génération et renouvellement SSL automatisé via challenge DNS-01 sur réseau interne non exposé.
  • Diagnostic et résolution d'incidents SSO par intervention directe en base PostgreSQL.
  • Conception d'un PRA complet : sauvegarde à chaud, rétention et externalisation NAS via SSH.
  • Nettoyage et intégrité de données à grande échelle par requêtes SQL de masse.
